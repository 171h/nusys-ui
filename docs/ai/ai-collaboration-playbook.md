# AI 协作与交付手册

本文档收敛 Nusys UI 仓库中 AI 编码代理与协作开发者反复使用的任务组织、工作区隔离、提交、评审、文档卫生与交付要求。它回答“怎么接任务、怎么隔离、怎么提交、怎么交付”，不重复组件实现细节；组件开发、测试、文档与发布规则分别以 [AGENTS.md](https://github.com/171h/nusys-ui/blob/main/AGENTS.md)、[CONTRIBUTING.md](https://github.com/171h/nusys-ui/blob/main/CONTRIBUTING.md) 和[文档维护](../guide/contributing.md)为准。

本文件是 [AGENTS.md](https://github.com/171h/nusys-ui/blob/main/AGENTS.md) 的配套细则。两者冲突时，按 §1 的优先级处理；同一规则只保留一处权威定义，其他地方使用链接。

## 1. 指令优先级与工作模式

- 优先级从高到低：用户当前任务的明确要求 → [AGENTS.md](https://github.com/171h/nusys-ui/blob/main/AGENTS.md) → 本手册 → `docs/` 领域文档与工具默认行为。冲突时先指出冲突点和推荐方案，不得静默选择一方。
- 默认直接实施。只有用户明确要求“先做计划”“先给方案”“进入计划模式”，或任务存在必须先由用户决定的产品/公共 API 分叉时，才先写计划并等待确认。
- 用户要求“先理解一下我的意思，翻译成你自己的理解发给我”时，先复述需求与验收点，确认后再改代码。
- 用户说“只回答”“不要修改代码”“只写文档”时是硬边界：不产生越界改动，也不顺手重构。
- 长提示词中的编号条目就是验收清单。实施时逐条覆盖，交付时逐条说明完成情况；不得只处理示例或只改界面。
- 需求涉及多个组件时，先判断是否存在同一根因、同一共享基类/工具或同一文档数据契约。优先修共享层并补齐所有调用方，避免逐个组件打补丁。
- 涉及不可逆、对外可见或高风险的操作（删除、推送、发布、修改 CI 或密钥等）仍需先确认。

## 2. 工作区与分支隔离

- 未明确要求在当前分支实施且任务需要隔离时，在 `G:\worktrees` 创建新工作区，名称为 `<主 worktree 名称>-<英文任务描述>`，本仓库使用 `nusys-ui-<英文任务描述>`，例如 `nusys-ui-ai-collaboration-guide`；分支使用 `<type>/<英文任务描述>`，从最新 `main` 创建。
- 用户指定 PR、已有 worktree 或已有分支时，在该工作区继续，不另建平行实现。
- 开工前检查 `git status --short`、当前分支和 `git worktree list`。工作区存在未提交改动时先判断归属，不覆盖或回退用户与其他代理的工作。
- 超过一个仓库的任务（例如组件库与宿主扩展）分别创建 worktree 和 PR，并在两个 PR 描述中互相链接；不要在一个仓库的提交里夹带另一个仓库的改动。
- 大范围移动、重命名或目录重构先单独提交“只移动”的变更，再提交内容修改，保证 Git 能追踪历史。
- 任务结束前清理本任务创建的临时分支、worktree 和未使用文件；保留用户明确要求保留的成果。

## 3. 提交与推送契约

- 每完成一个可独立验收的任务提交一次。多任务提示词不得在最后压成一个巨型提交；同一任务的实现、测试和文档可以放在同一提交或相邻提交。
- 提交前只暂存本任务相关文件，不提交 `tmp/`、`logs/`、`.cache/`、`dist/`、`custom-elements.json`、`vscode.*-custom-data.json`、`docs/api/generated/`、`docs/public/assets/`、编辑器临时文件或无关格式化。
- Commit Message 遵循 [AGENTS.md](https://github.com/171h/nusys-ui/blob/main/AGENTS.md#提交信息规范) 的 Conventional Commits 规则并使用中文：`type(scope): subject`。`subject` 简洁、不以句号结尾；需要说明原因、影响范围或迁移边界时写中文正文。
- PR Title 与 Commit Message 使用同一套 Conventional Commits 规则，必须为中文；不得使用“修复一些问题”“完善功能”等无类型、无主题的标题。PR Description 使用中文，至少说明变更内容、验证结果、公共 API 兼容性与无障碍影响。
- 用户要求“每完成一个任务就提交，全部完成后统一推送”时，严格按此执行：过程只本地提交，最后统一推送任务分支；不要提前推送，也不要推送 `main`。
- 未经明确要求不强制推送、不推送主分支、不自动合并 PR、不执行发布。发布和标签推送失败时，输出可直接复制的补推命令，并说明发布工作流尚未成功。
- 推送后核对远程分支与 PR 状态；交付中给出提交哈希和推送结果，不只写“已完成”。

### 3.1 验证矩阵与仓库门禁

完整门禁与 CI 保持一致，命令来自 [verify.yml](https://github.com/171h/nusys-ui/blob/main/.github/workflows/verify.yml) 和 [docs.yml](https://github.com/171h/nusys-ui/blob/main/.github/workflows/docs.yml)：

```text
pnpm install --frozen-lockfile
pnpm test:install
pnpm build
pnpm typecheck
pnpm lint
pnpm prettier
pnpm docs:check
pnpm docs:test
pnpm docs:test:dev
pnpm test:build
pnpm test
```

准备 PR、请求合并或声称任务完成前，必须通过完整门禁；日常迭代至少执行与变更范围对应的检查：

| 变更范围                     | 至少执行                                                                                                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 组件源码、共享工具、公共导出 | `pnpm lint`、`pnpm prettier`、`pnpm typecheck`、`pnpm build`、`pnpm test`、`pnpm test:build`；影响示例或公共文档时再加 `pnpm docs:check`、`pnpm docs:test` |
| 文档、示例与演示数据         | `pnpm prettier`、`pnpm docs:check`、`pnpm docs:test`；修改文档监听、热更新或构建配置时再加 `pnpm docs:test:dev`                                            |
| 发布脚本、构建或元数据脚本   | `pnpm prettier`、`pnpm test:release`、`pnpm build`、`pnpm test:build`；涉及组件行为时再加 `pnpm test`                                                      |
| CI、Pages 或发布工作流       | 对应工作流中的完整命令；至少覆盖受影响的验证与文档命令                                                                                                     |

首次安装依赖或缺少浏览器时，先执行 `pnpm install --frozen-lockfile` 与 `pnpm test:install`。未实际运行的检查不得写成通过；缺少依赖或无法访问浏览器时，应说明原因和影响范围。

## 4. 代码评审与 PR 合并

### 4.1 评审范围与准备

- 只评审本次变更（最近编写或修改的代码、staged changes 或用户指定范围），不审查相邻代码或整个代码库。
- 评审前先读 [AGENTS.md](https://github.com/171h/nusys-ui/blob/main/AGENTS.md)，再按变更范围加载对应文档：组件公共 API 与兼容性看组件文档，文档与示例看[文档维护](../guide/contributing.md)，发布工具看 `scripts/release.mjs` 与发布工作流。
- 评审前按 §3.1 运行门禁。任一必跑命令失败均列为 🔴 必须修复，不得给出可合并结论。
- 门禁结论必须基于当前 PR 的真实内容；未实际运行的检查不得写成通过。

### 4.2 审查重点

逐项核对本次变更，具体判定标准以对应文档为准：

- 公共 API 兼容性：标签名、属性与反射特性、属性类型、事件及 `detail`、插槽、CSS 部件、CSS 自定义属性、默认值和导出类型。
- Lit 正确性：响应式属性声明、`updateComplete`、生命周期、事件监听与清理、`disconnectedCallback`、表单关联和原生事件语义。
- 无障碍：可访问名称、ARIA 语义、键盘操作、焦点管理、禁用状态、屏幕阅读器可理解性。
- 样式与主题：VS Code 主题变量及回退值、明暗与高对比度、尺寸变化、固定颜色和硬编码像素。
- 测试：默认值、边界值、非法输入、禁用、键盘、表单提交与旧行为回归；测试可观察行为，不绑定私有实现。
- 文档与示例：组件页、`docs/data/examples.mjs`、`scenarios.mjs`、`showcase.mjs`、生成 API、本地链接和 CSP 约束。
- 安全性：不可信 HTML、用户输入清理、Webview 消息校验、凭据与敏感信息泄露。
- 代码质量与性能：命名一致性、合理复用、死代码、无效注释、阻塞主线程或重复渲染。
- TypeScript：类型准确、避免 `any`、合理使用类型推断与泛型。

### 4.3 输出与修复闭环

- 涉及 PR 时，评审结论必须用中文写到 PR 页面（review 或 PR 评论），不得只留在对话或终端输出；按 🔴 必须修复、🟡 建议改进、🟢 积极观察分类，必要时补充 💡 问题与思考。必须修复项要给出文件、位置、原因和验证方式。仅本地审查时，把同样结构写进交付报告。
- 每次评审都给出可直接使用的单行中文 PR 标题（Conventional Commits）与匹配的提交标题、提交正文；即使存在阻塞项也要给出基于“合入后形态”的提交建议，并明确应先修复再提交。
- 处理评审意见前先判断是否真实存在。真实存在才修改；不存在的说明理由并忽略，不为迎合意见引入错误改动。
- 修复一个独立问题提交一次，提交信息说明对应评审点；修复后在 PR 中回复并 resolve conversation。
- 修复完成后再次评审同一 PR，重复“评审 → 修复 → 回复”直到没有阻塞项，再回答是否具备合并条件。
- 不把“评审意见已处理”当成“功能已验证”。仍需运行门禁并说明实际验证范围。

### 4.4 合并策略

- 用户要求将 PR 合并到 `main` 时，默认使用 `Merge pull request`（Create a merge commit）；不得擅自改为 `Squash and merge` 或 `Rebase and merge`。
- 仅当 PR 只包含 1 个提交，或用户明确要求 `Squash and merge` / `Rebase and merge` 时，才考虑对应策略；采用前确认提交历史与提交语义完整。
- 合并前确认没有阻塞项、门禁通过，并已取得用户明确授权；未经明确要求不自动合并 PR。
- 使用 `Merge pull request` 时，必须通过 `gh pr merge <PR> --merge --body-file <文件>` 为合并提交补充完整中文正文：首行使用与 PR 对应的 Conventional Commits 中文摘要，随后按组件或文档模块列出该 PR 的全部变更。不得只保留自动生成的 `Merge pull request #...` 标题或单行描述。
- 用户要求生成合并描述时，按实际采用策略的语义生成中文描述，不混用三种策略。

## 5. 任务拆解与“全面排查”

- “全面排查”“一次修复彻底”表示要覆盖同一根因的所有层级：共享基类与工具、组件实现、样式、类型与导出、测试、组件文档、示例数据、场景登记、综合体验页、生成 API 与 VS Code 补全数据。
- 修复前先定位权威来源：共享基类、工具函数、组件实现或 `docs/data/` 中的哪一份数据是唯一来源；修复后所有调用方走同一入口，不复制分支逻辑。
- 新增组件优先复用最接近的完整切片：表单控件参考 `src/vscode-textfield/`，复杂键盘与拖拽交互参考 `src/vscode-tabs/`，组合布局与分组参考 `src/vscode-ribbon/`。复用其基类、样式、测试、文档和示例流程，不自造第二套结构。
- 同一行为在属性、属性反射、方法、事件和表单提交中的语义必须一致；差异只允许来自平台或原生控件约束，并写明原因。
- 用户报告“某个属性没用/事件没触发/文档没体现”时，检查“源码 → 渲染与样式 → 事件 → JSDoc → 自定义元素清单 → 组件文档 → 示例与场景 → 生成 API/补全数据”整条链路，而不是只改显示。
- 涉及交互或公共行为的修改必须补测试，至少覆盖默认值、边界值、非法输入、禁用状态、键盘操作和旧行为回归；只改文案或样式也要验证主题、尺寸与交互。

## 6. 常见任务执行清单

### 6.1 组件行为调整或缺陷修复

1. 先读组件源码、样式、测试、组件文档、`docs/data/examples.mjs` 与 `scenarios.mjs`，确认当前行为和公共契约。
2. 判断根因在共享基类/工具还是单个组件；共享问题先修共享层并补齐所有调用方。
3. 保持标签名、属性、反射特性、事件、插槽、CSS 部件和导出兼容；破坏性变更先说明迁移步骤。
4. 为行为变化补回归测试，覆盖默认值、边界、非法输入、禁用、键盘与表单关联；等待 Lit 更新后再断言。
5. 同步 JSDoc、组件文档、示例和场景；仅在行为或公共 API 变化时更新说明文档。
6. 执行 §3.1 的检查，并验证明暗主题、高对比度、尺寸、焦点和禁用状态。

### 6.2 新增组件或公共 API

1. 选最接近的完整组件切片（表单控件参考 `vscode-textfield`，复杂交互参考 `vscode-tabs`，组合布局参考 `vscode-ribbon`），复用基类、样式和测试模式。
2. 先定义标签、属性与反射、事件 `detail`、插槽、CSS 部件、CSS 自定义属性、可访问名称和键盘行为。
3. 新增 `src/vscode-*/`（实现、样式、`index.ts`、测试），在 `src/main.ts` 导出组件和公共类型。
4. 在 `docs/data/components.mjs`、`examples.mjs`、`scenarios.mjs`、`showcase.mjs` 登记；新增组件文档页，并包含 `<ComponentExamples component="..." />`。
5. 用现有脚本生成 `custom-elements.json`、`vscode.*-custom-data.json` 和 `docs/api/generated/`，不手改生成物。
6. 执行 `pnpm docs:check`、`pnpm docs:test`、`pnpm test:build` 与完整门禁；破坏性变更补迁移说明和变更日志。

### 6.3 文档与示例

1. 示例与场景的唯一数据源是 `docs/data/*.mjs` 和组件 Markdown；不要在多处复制同一示例或参数说明。
2. 示例只使用仓库维护者审核的静态 HTML/CSS/JS；不执行外部用户输入，不使用不可信 HTML。
3. 说明、注释和示例文案使用中文；主题选择器只在全局布局维护，不在组件页重复挂载。
4. 检查明暗主题、尺寸、键盘、焦点和禁用状态；涉及表单时验证真实 `FormData`，不要只读取控件的 `value`。
5. 执行 `pnpm prettier`、`pnpm docs:check`、`pnpm docs:test`；修改热更新、监听或文档构建配置时执行 `pnpm docs:test:dev`。
6. 更新 `docs/.vitepress/config.mts` 侧边栏与本地链接，确保新页面可导航。

### 6.4 发布与工具链

1. 仅在用户明确授权时运行 `pnpm release`；脚本会更新版本与变更日志、创建提交和标签，并可能推送。
2. 修改 `scripts/release.mjs` 等发布工具时执行 `pnpm test:release`，并在交付中说明是否实际运行。
3. 标签推送触发 Release 工作流；本地推送成功不等于 npm 发布完成，需检查工作流结果。
4. 不擅自修改包版本、替换标签或发布包。

### 6.5 评审与修复评审意见

1. 先复现或核对意见是否真实存在，再决定修改或说明忽略理由。
2. 每个独立问题一个提交；修复后在 PR 回复并 resolve conversation。
3. 修完重新评审同一 PR，直到没有阻塞项；不得只处理“必须修复”而遗漏同一根因的其他位置。

### 6.6 文档与规范整理

1. 先确定单一真相源：仓库规则在 [AGENTS.md](https://github.com/171h/nusys-ui/blob/main/AGENTS.md)，协作流程在本手册，组件与文档规则在 [CONTRIBUTING.md](https://github.com/171h/nusys-ui/blob/main/CONTRIBUTING.md) 和[文档维护](../guide/contributing.md)，过程材料在 `tmp/`。
2. 删除重复段落而不是再写一份“摘要”；保留的规则只出现一次，其他位置用链接。
3. 更新文档地图、VitePress 侧边栏、相对链接和失效路径；执行 `pnpm docs:check`。
4. 不把思考过程、修改历史、临时计划和评审对话写进正式文档。

## 7. 代码与注释卫生

- 新建或大幅修改的 `.ts`、`.mjs`、`.mts` 文件写中文文件级注释，说明“这是什么、负责什么”；带 shebang 的脚本把注释放在 shebang 之后。已有但不在顶部的描述性注释按用户要求处理：只把文件级说明放顶部，其他既有注释保留原位置。
- 注释只描述最终代码的行为、约束和原因，不写修改过程。禁止“移至原位置”“原先是……”“新增一个……”“已对齐”等变更叙事；代码里不保留调试笔记和一次性待办。
- 公共 API 的 JSDoc 使用中文说明默认值、属性反射、事件、插槽、CSS 部件与无障碍语义；保留 `@param`、`@returns`、`@slot` 等标签格式。
- 不硬编码颜色、尺寸或业务默认值；颜色使用 VS Code 主题变量与现有回退值，尺寸使用组件尺寸属性或共享样式变量。
- 不新增“看起来有用但不参与行为”的属性、方法或示例参数。每个公共 API 都必须实现、测试并记录。
- 输入 `0`、空值和“未设置”必须区分：`0` 是真实数值，`undefined`、`null`、空字符串和非有限数不得静默转成 `0`；默认值必须在源码、JSDoc、文档和测试中保持一致。

## 8. 公共 API、默认值与兼容性

- 公共契约包括标签名、属性与反射特性、属性类型、事件及 `detail`、插槽、CSS 部件、CSS 自定义属性、默认值、导出类型和可访问名称。
- 默认值必须同时体现在源码、JSDoc、组件文档、示例和生成的元素清单中；行为变化时补测试，不只改说明。
- 破坏性变更必须说明影响、迁移步骤和兼容层安排；面向使用者的变化同步更新 `CHANGELOG.md`。
- `dist/`、`custom-elements.json`、`vscode.*-custom-data.json`、`docs/api/generated/` 和 `docs/public/assets/` 一律由脚本生成，不手动修改或提交。
- 修改公共 API 后执行 `pnpm build`、`pnpm docs:prepare` 或完整文档流程，确认元素清单、VS Code 补全数据和 API 页面同步更新。

## 9. 文档与临时材料

- `docs/` 只保留现行开发指南、组件文档、正式说明、长期技术报告和示例数据。临时评审意见、重构方案、一次性迁移记录、任务交接、修复记录和验收台账一律放根目录 `tmp/`，按任务建子目录，且不被 Git 追踪。已经作为正式技术报告维护并加入导航的迁移说明可以保留在 `docs/`，但只记录最终结论与现行约束。
- 开发日志写 `logs/<任务名>/`，工具缓存写 `.cache/`；不在仓库根目录散落 `*.log`、`*.tmp`、调试 HTML/JSON 或截图。
- 新写或修改的开发文档只写最终事实：当前属性、事件、默认值、路径、适用条件和验证方式。禁止写“之前是……现在改为……”“不是先前假设的……”“已对齐”等过程叙述。
- 修改架构、目录、命令、公共 API 或文档链接时，同步更新 [AGENTS.md](https://github.com/171h/nusys-ui/blob/main/AGENTS.md) 文档地图、`docs/.vitepress/config.mts` 导航和受影响指南，避免留下失效路径。
- 新增长期文档必须加入 `docs/.vitepress/config.mts` 的对应侧边栏；临时文档不得加入导航。
- 面向使用者的变更按贡献指南维护 `CHANGELOG.md`；发布工具按提交类型分组生成变更日志。

## 10. 交付报告

任务结束时用中文简要报告：

1. 已完成内容，对应提示词编号或验收项。
2. 关键改动文件与提交哈希。
3. 实际运行的检查、测试和构建结果；未运行项及原因。
4. 推送/PR 状态，或明确说明仅在本地提交。
5. 未完成项、已知限制和需要用户决策的事项。

不得用“应该可以”“理论上通过”代替实际验证结果。
